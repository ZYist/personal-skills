# 审查当前分支变更

## 前置条件
- 当前工作目录是一个 git 仓库
- 存在未提交或未合并的变更
- 已读 `rules/review-rules.md` 和 `references/gotchas.md`

## 流程

### Step 1: 确定审查范围

1. 获取当前分支名：`git branch --show-current`
2. 确定对比基准：
   - 如果有 main/master 分支 → `git diff origin/main...HEAD`
   - 如果没有 → `git diff HEAD~1...HEAD`（最后一次提交）
   - 如果用户指定了对比分支 → 使用用户指定的分支
3. 获取变更文件列表：`git diff --name-status`
4. 按 `rules/review-rules.md` 第六节排除规则过滤文件

**⚠️ 失败分支**：
- 仓库没有提交历史 → 告知用户"仓库为空，无变更可审查"，终止
- 没有变更文件 → 告知用户"没有检测到变更"，终止
- diff 超过 2000 行 → 触发分批策略（见 Step 1b）

### Step 1b: 巨型 Diff 分批策略

当 diff 超过 2000 行时：
1. 按文件将变更分成批次，每批不超过 500 行 diff
2. 优先审查 `.py`、`.js`、`.ts`、`.java`、`.go`、`.rs` 等源代码文件
3. 每批独立审查，最后合并报告
4. 告知用户"变更量较大（X 行），分 Y 批审查"

### Step 2: 读取变更上下文

对每个变更文件：
1. 读取完整 diff：`git diff <file>`
2. 读取变更涉及的函数/方法的完整定义（不只是变更行）
3. 新增文件读取完整内容

**⚠️ 失败分支**：
- 文件内容无法读取（二进制、编码问题） → 跳过该文件，在报告中标注"跳过：无法读取"

### Step 3: 按维度审查

对每个文件，按 `rules/review-rules.md` 第一节的四个维度逐一检查：

**Bug 风险检查清单**：
- 空指针/None 引用
- 数组越界/下标未校验
- 未处理的异常/错误
- 竞态条件（共享状态 + 并发）
- 资源泄露（未关闭的连接、文件句柄）
- 类型混淆
- 逻辑条件错误（off-by-one、条件取反）
- 未处理的边界情况

**安全漏洞检查清单**：
- SQL 拼接（非参数化查询）
- XSS（未转义的用户输入直接渲染）
- 命令注入（exec/system 调用含用户输入）
- 硬编码密钥/密码/token
- 不安全的反序列化
- 路径遍历
- 权限校验缺失

**性能问题检查清单**：
- 循环内的数据库查询（N+1）
- 循环内的重复计算
- 不必要的同步/阻塞操作
- 大对象复制（可用引用替代）
- 缺少分页/限制的查询
- 内存泄漏模式（全局缓存无淘汰）

**代码风格检查清单**：
- 函数/方法超过 50 行
- 嵌套超过 4 层
- 魔法数字/字符串（未定义为常量）
- 重复代码块
- 不清晰的命名（单字母变量、缩写）
- 缺少必要的注释（复杂逻辑未注释）

### Step 4: 生成报告

按 `rules/review-rules.md` 第四节和第五节的格式生成结构化报告。

检查整体评估：
- 存在 Critical → FAIL
- 存在 High 且严格度 >= medium → PASS WITH WARNINGS
- 其他 → PASS

### Step 5: 🔴 CHECKPOINT — 输出报告

向用户展示完整报告。如果评估为 FAIL：
1. 高亮 Critical 发现
2. 询问用户："存在 X 个 Critical 问题，建议修复后再提交。是否需要自动修复？"
3. 用户确认修复 → 对每个 Critical 发现生成代码修改建议并应用

用户确认无需修复或报告为 PASS → 完成。
