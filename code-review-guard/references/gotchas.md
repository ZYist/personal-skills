# Code Review Guard 踩坑清单

---

## 命名：huge-diff-overload — 巨型 Diff 导致审查遗漏

**触发条件**：一次审查超过 2000 行 diff

**根因**：上下文窗口有限，大量代码同时审查时 Agent 对每段代码的关注度下降，Critical 问题可能被忽略

**后果**：审查报告给出 PASS，但实际存在严重问题

**解决**：
- diff 超过 2000 行时强制分批（每批 <= 500 行）
- 按文件分批，不按行号切割（保持文件上下文完整）
- 每批独立审查，最后合并去重报告
- 在报告摘要中标注"分批审查：X 批 / Y 文件"

---

## 命名：false-positive-flood — 误报淹没真实问题

**触发条件**：严格度为 high 时对风格问题过度报告

**根因**：High 严格度报告所有 Low 级发现，大量命名/风格建议淹没了真正的 bug 和安全问题

**后果**：用户不再认真阅读报告，Critical 发现被忽略

**解决**：
- 即使严格度为 high，报告仍然按严重度排序（Critical 在前，Low 在后）
- 摘要区只显示 Critical 和 High 的数量，Low 数量折叠
- 每个文件最多报告 5 个 Low 发现，超出部分只给计数
- 建议用户使用 medium 严格度配合 `.code-review-guard.json` 自定义阈值

---

## 命名：report-without-fix — 只查不改

**触发条件**：审查报告列出了问题但没有给出可操作的修复方案

**根因**：Agent 列出问题后直接结束，认为"报告完毕"

**后果**：用户知道有问题但不知道怎么改，审查沦为形式

**解决**：
- 每个发现必须有 `修复建议` 字段，包含以下之一：
  - 可直接替换的代码片段
  - 明确的修改步骤（"将 X 改为 Y"）
  - 对于架构级问题，给出重构方向和拆分建议
- Critical 发现必须主动询问用户是否需要自动修复
- 报告结尾提供"快速修复摘要"：所有可自动修复的发现汇总

---

## 命名：diff-only-trap — 只看 Diff 不看上下文

**触发条件**：只通过 `git diff` 输出审查，不读取文件完整内容

**根因**：diff 只显示变更行，缺少函数签名、类定义、调用链等上下文

**后果**：
- 误报：变量看起来未初始化，但实际在 diff 之外的构造函数中初始化
- 漏检：变更行本身无问题，但函数缺少异常处理（只在完整函数定义中可见）

**解决**：
- 对变更文件读取完整内容（新增文件）或变更涉及的完整函数定义（修改文件）
- diff 作为"关注点定位"工具，不作为唯一信息源
- 变更行少于 5 行时尤其需要读取上下文（小改动更容易遗漏影响）

---

## 命名：skip-generated-files — 审查生成文件浪费时间

**触发条件**：diff 中包含自动生成的文件（如 lock 文件、编译产物、protobuf 生成代码）

**根因**：生成文件的"问题"不应通过手动修改来解决，应该修改生成器或配置

**后果**：审查报告充满无关发现，降低可信度

**解决**：
- 严格遵守 `rules/review-rules.md` 第六节的排除规则
- 无法自动判断时检查文件头部的 `@generated`、`auto-generated`、`DO NOT EDIT` 标记
- 对不确定的文件，在报告中标注"疑似生成文件，已跳过"

---

## 命名：language-blind — 不考虑语言特性

**触发条件**：用同一套规则审查所有语言，不考虑语言差异

**根因**：Python 的"问题"在 Rust 中可能是正常模式（如隐式类型转换 vs 显式类型）

**后果**：大量无效发现，用户对审查失去信心

**解决**：
- 根据文件扩展名识别语言
- 按语言调整检查标准：
  - Python：关注动态类型问题、GIL 相关并发陷阱
  - JavaScript/TypeScript：关注 undefined/null、异步异常处理、原型链问题
  - Java：关注空指针、资源泄露（try-with-resources）、线程安全
  - Go：关注未检查的 error、goroutine 泄漏、竞态条件
  - Rust：关注 unsafe 块、unwrap 调用、生命周期问题
- 检查清单中的每项只在适用语言时报告
