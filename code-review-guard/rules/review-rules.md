# Code Review Guard 核心规则

## 一、审查维度

每次审查覆盖以下四个维度，不可跳过任何一个：

1. **Bug 风险** — 逻辑错误、空指针、越界、竞态条件、资源泄露
2. **安全漏洞** — 注入攻击（SQL/XSS/命令注入）、硬编码密钥、不安全的反序列化、权限绕过
3. **性能问题** — N+1 查询、内存泄漏、不必要的同步操作、大循环内的重复计算
4. **代码风格** — 命名规范、函数长度、重复代码、过度嵌套、魔法数字

每个维度发现的问题都必须报告，即使其他维度零发现。

## 二、严重度分级

所有发现按以下四级分类：

| 级别 | 标签 | 含义 | 要求 |
|------|------|------|------|
| Critical | `[CRITICAL]` | 必定导致运行时崩溃或安全漏洞 | 必须修复后才能提交 |
| High | `[HIGH]` | 高概率导致 bug 或显著性能退化 | 强烈建议修复 |
| Medium | `[MEDIUM]` | 可能引发问题或降低可维护性 | 建议修复 |
| Low | `[LOW]` | 代码风格、可读性改进 | 可选修复 |

**为什么需要分级**：不分级导致所有发现等同视之，Critical 问题淹没在 Low 建议中。

## 三、严格度配置

严格度控制报告的最低严重度门槛：

| 严格度 | 报告门槛 | 适用场景 |
|--------|---------|---------|
| `low` | Critical + High | 快速迭代阶段，只关注阻断性问题 |
| `medium`（默认） | Critical + High + Medium | 常规开发，平衡速度与质量 |
| `high` | 所有级别 | 合规要求高、核心模块、发布分支 |

用户未指定严格度时使用 `medium`。

## 四、输出格式

每个发现必须包含以下结构化字段，不可省略任何一项：

```
### [级别] 简短标题
- **文件**: 文件路径:行号
- **类别**: bug-risk / security / performance / style
- **问题**: 描述具体问题（1-2 句）
- **修复建议**: 给出可直接替换的代码片段或明确的修改方向
```

**为什么需要代码片段**：只说"这里有问题"不给修法，报告就只是噪音。

## 五、审查报告结构

报告按以下顺序组织：

1. **摘要** — 文件数、发现总数（按级别统计）、整体评估（PASS / PASS WITH WARNINGS / FAIL）
2. **Critical 发现** — 按文件分组
3. **High 发现** — 按文件分组
4. **Medium 发现** — 按文件分组（严格度 >= medium 时）
5. **Low 发现** — 按文件分组（严格度 = high 时）
6. **统计** — 各维度发现数量、各文件发现数量

整体评估规则：
- 存在 Critical 发现 → FAIL
- 存在 High 发现且严格度 >= medium → PASS WITH WARNINGS
- 其他 → PASS

## 六、排除规则

以下内容不审查，直接跳过：
- `node_modules/`、`vendor/`、`dist/`、`build/`、`.git/` 目录
- 自动生成的文件（`*.min.js`、`*.generated.*`、`package-lock.json`）
- 二进制文件、图片、字体文件
- 仅含空白或格式变更的行（除非严格度为 high）

## 七、上下文读取

审查时读取变更文件的实际内容，不能只看 diff 行。原因：
- diff 只显示变更行，缺少函数签名、类定义、调用链上下文
- 无法判断变量是否初始化、异常是否被捕获
- 只看 diff 会导致大量误报和漏报

对于新增文件，读取完整文件内容。对于修改的文件，读取变更涉及的函数/方法的完整定义。
